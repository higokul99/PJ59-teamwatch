# Technical Interview Notes: Multi-Episode Watch Rooms

- Status: MVP implemented locally; production performance is not benchmarked
- Date: 13 November 2026
- Scope: [Room Series Library PRD](prd.md)

## Short explanation

“I separated a room's media library from its active playback selection. Each episode has independent storage and preparation state, while the room owns one active episode and one authoritative timeline. A bounded server-wide worker queue prepares episodes, and WebSocket events synchronize episode changes and playback across participants.”

The retained library and manual episode sequencing are implemented locally. Distinguish this from deployment and production benchmarking, which have not been performed for this feature. Autoplay and distributed processing remain future work.

## Why this design

A playlist is not just an array of filenames. The design must separate persistent content, long-running preparation work and short-lived synchronized playback. Otherwise an upload could replace active content, a delayed readiness message could affect the wrong episode, or a restart could lose queued work.

Keep the initial deployment as one FastAPI process with explicit dependencies between room services and admin routes. A folder boundary does not provide process isolation. Moving workers into separate processes is a future option, not a requirement to deliver the first library implementation.

## Implemented persistent model

- `episodes`: immutable episode ID, room ID, title, ordinal, job status, generation, current asset ID, retained source filename, media metadata JSON, progress JSON, error and creation time.
- `episode_selection`: room ID, active episode ID and persistent selection revision. Restart restores the selection but starts paused at zero.
- Existing room/account records control authorization; passwords and roles are not duplicated.

The MVP keeps durable job status on the episode itself rather than introducing a separate jobs table. One global worker selects queued rows, rotates between rooms and prioritizes upcoming content within each room. A new generation receives a new asset ID on retry, preventing stale browser caches from referring to regenerated bytes. Sources are retained until deletion.

Application locks serialize selection/deletion/reordering; SQLite transactions persist state transitions. All file paths are generated by the server. Filesystem failures are represented as cleanup-pending records rather than false success.

## Implemented API surface

These viewer endpoints are implemented; upload bodies stream raw file bytes with a `name` query parameter:

- `GET /api/episodes`: list the authenticated room's library and readiness.
- `POST /api/episodes`: accept a new episode upload and return its ID; preparation runs asynchronously.
- `PATCH /api/episodes/{id}`: update title.
- `PUT /api/episodes/order`: atomically replace order with a validated list of that room's episode IDs.
- `POST /api/episodes/{id}/select`: switch the room's active episode.
- `POST /api/episodes/{id}/retry`: retry eligible failed preparation.
- `DELETE /api/episodes/{id}`: delete an episode after authorization and any required active-playback confirmation.
- `DELETE /api/episodes`: delete the library with an exact confirmation value.

Upload, edit, select, retry and delete require host or admin authority. Listing and media delivery require valid room membership. Apply origin checks, input validation, request limits and quotas on the server. Admin routes should call the same library service rather than implement a second deletion pipeline.

## Upload and worker lifecycle

Stream an upload to a temporary file; do not buffer the entire movie in RAM. Enforce byte limits while receiving, reserve storage budget and publish the completed upload before enqueueing preparation. Handle the database/filesystem boundary with explicit intermediate states and reconciliation; a database transaction alone cannot roll back filesystem changes.

A durable job moves through queued, running and completed/failed states. The implementation runs one active encoder globally to protect playback and prevent eight episodes from launching eight FFmpeg processes. Prioritize the selected queued episode and then upcoming content, while giving other rooms a fair turn. Do not terminate a running conversion solely because another episode is selected.

Workers use the existing FFprobe/FFmpeg pipeline. Compatible tracks can be copied; others are converted into HLS fragmented MP4 segments. Publish only complete segments. Available duration is the minimum prepared duration across required audio/video tracks, preventing the UI from advertising video for which audio is unavailable.

The original upload must be retained while a retry remains possible, or the UI must explicitly request reupload. Delete source files according to an explicit storage policy, not accidentally as a side effect of an unsuccessful job.

## Synchronized episode switch

1. Authorize the host and verify that the episode belongs to the room and has a playable prefix.
2. Serialize selection against concurrent switches/deletion using a room-level lock.
3. Update active ID, pause at zero and increment the selection/timeline revision.
4. Clear device readiness and broadcast a single authoritative snapshot.
5. Clients stop old players/download tasks, load the selected playlist and report readiness for that episode and revision.
6. Accept Play when the existing readiness rules allow it; schedule the shared start using the server timeline.

Every readiness/control message carries the episode ID and revision. Reject stale messages. A participant's old “ready” event must never satisfy the new episode's start barrier. Late joiners receive the current snapshot rather than replaying historical switches.

## Deletion, retries and recovery

Deleting active content pauses the room and clears its active selection. Invalidate the episode/job generation before cancelling workers so a late worker cannot republish deleted media. Reject new requests for that episode, then clean files. Use a tombstone/cleanup-pending state to retry disk failures safely; cache authorization checks must also reject deleted media.

On startup, reconcile queued/running jobs, manifests and temporary files. Only one worker may own a job generation. Completed episodes remain usable. Interrupted output must either be finalized as explicitly incomplete or regenerated into a new generation; never append blindly to an unknown partial playlist.

Migrate the current active movie into one library entry without deleting existing media. Test migration and rollback against a copy of real data. An older single-movie release cannot understand new library records; code rollback alone does not reverse data changes.

## Trade-offs to explain

- SQLite is practical for a single-process MVP, but long writes and database lock contention can hurt latency. Keep transactions short; move costly hashing/file work off the event loop.
- One encoder protects CPU and memory but increases queue delay. Increase concurrency only after measurements, not based on upload count.
- Early playback reduces startup waiting but can catch up with preparation. Full preparation avoids processing-related stalls, not network/device stalls.
- Retaining episodes improves usability but increases disk usage. Quotas must include source files, output segments and temporary work.
- WebSockets carry control and status; HTTP serves media. Sending movie bytes through the control channel would complicate buffering and scale poorly.
- Redis, a separate job broker, object storage and independent workers become useful if multiple API processes or machines are required. They are not claimed capabilities of this MVP.

## Tests and observability

Test eight retained episodes, two-room isolation, unauthorized selection, concurrent reorder/switch/delete, stale events, active deletion, partial-preparation failure, retries, quota rejection, disk-full behavior and restart recovery. Include actual FFmpeg fixtures and real-browser checks on desktop and mobile.

Track upload completion, queue wait, first-playable latency, preparation speed, prepared-ahead duration, encoder failures, storage usage and playback stalls. Correlate logs with room, episode, job and generation IDs; exclude passcodes, cookies and private filenames where unnecessary.

Do not claim a performance improvement until measured. A strong interview answer explains the target, the failure modes, the chosen trade-offs and how tests/metrics would prove the implementation works.


## Scope of verification

Automated tests exercise eight real FFmpeg uploads, explicit selection, retained prior media, participant/cross-room rejection, stale WebSocket events, restart recovery, single-worker fairness, retry generations, deletion cleanup failures and quota rejection. Browser checks cover host selection, Next confirmation and the 375px layout. These checks establish functional behavior, not long-movie throughput or multi-machine scalability.
