# Production release candidate — 12 November 2026

Status: local verification completed on 13 November 2026; production has not been changed. This candidate is the current working tree, not yet an immutable Git release. Include all intended modified/new files (including documentation moves) in a reviewed commit before deployment. Do not commit `.env`, uploads, databases or local logs.

## Included behavior

- Dedicated admin authentication, room and host/participant account management, audit history, and media controls.
- Separate playback/media state per room and hashed persistent account credentials in SQLite.
- Incremental HLS preparation with host-visible prepared duration, remaining duration and full-movie readiness.
- Shared static asset handling and safeguards against admin stalls and retained room runtimes.
- Deployment paths corrected to `docs/deployment`; Nginx handles both viewer and admin WebSockets, with backup of the known managed configuration before migration.
- Viewer login accepts the same 4–16-digit passcodes supported by account management.

## Deployment order

1. Commit and push the reviewed candidate to `origin/main`. Record its SHA; avoid adding secrets or runtime files.
2. Run `./deploy.sh test`. This builds/runs the Linux Docker tests on the VPS, builds the production image, deploys staging, and checks HTTPS, admin assets, and unauthenticated admin API rejection. Local image tags are for verification only; production uses the image tagged with the tested Git SHA on the VPS.
3. Initialize the staging admin password if necessary: from the staging checkout, run `docker compose --project-name teamwatch-test exec teamwatch python -m admin_portal set-password`.
4. On the staging HTTPS site, verify host/participant login, a passcode longer than four digits, two-room isolation, uploads/replacement/deletion, all three playback modes, late join, pause/seek/sync, prepared-duration warnings, and full readiness. Verify admin live updates through Nginx and reconnect after a network interruption. Use a real phone as well as desktop, and test the actual long movie before relying on preparation throughput.
5. Schedule a quiet window: finish uploads/conversion and inform active viewers that the restart disconnects them and restores playback paused.
6. Back up the stopped **production** data volume and `.env` to a protected location. Include `admin.sqlite3`, any WAL files, `current.json`, media folders and `rooms/`. See the deployment README; never delete the volume.
7. Run `./deploy.sh prod` for the same tested SHA. The existing `DEPLOY` prompt is the final activation confirmation. The helper reuses the tested image and attempts code/config recovery if health checks fail.
8. Initialize the production admin password separately if needed, using `teamwatch-prod`. Confirm admin login, viewer login, live updates, media playback and server logs over production HTTPS.

## Rollback

Run `./deploy.sh rollback` and confirm `ROLLBACK`. Keep the previous SHA/image and backup. Code rollback retains the data volume; it does not restore deleted media or undo account changes. An old single-room release cannot use newly created rooms or admin accounts and uses the old `.env` PINs. Restore data only while stopped and only from a verified backup for the correct environment; preserve UID 10001 ownership. Do not prune images or volumes during this release.

## Release gates

- Local unit/integration checks and production-container smoke checks: results recorded below after execution.
- VPS build/test and staging HTTPS/real-device acceptance: required before production activation; not run during local preparation.
- Production backup and initial admin password: operator steps at the maintenance window.
- Local tests do not establish production capacity, long-movie conversion speed, or process-level fault isolation.
